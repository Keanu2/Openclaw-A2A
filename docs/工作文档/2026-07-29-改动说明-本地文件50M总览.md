#### C.0 `TOOLS.md` 修改原因 & 为什么这么做（重点）

**修改原因（当时遇到的实际问题）：**

1. **聊天里 Agent 不会正确发本地文件**  
   用户说「把桌面/图库某文件发给对端」时，模型常去调 SoftBus、或 `a2a_send_file`（要公网 URI）、或自己拼超长 base64 塞进 `a2a.send`——后两种要么失败，要么撞 ARG_MAX。  
   → 所以在 TOOLS 里**写死**：本地文件**必须**用 `a2a_send_local_file`，并写明绝对路径示例。

2. **「没有配对 / 没权限」类错误话术**  
   SoftBus 插件异常或未配对时，模型会把 A2A 失败归因成「设备没配对」。其实 A2A peer（`HW-PC1`/`HW-Phone1`）与 SoftBus 无关。  
   → TOOLS/MEMORY 明确：**A2A 名不是 SoftBus**；禁止配对话术；手机侧 SoftBus 已关。

3. **路径找错或幻觉造文件**  
   HarmonyOS 桌面/图库路径不直观；模型找不到文件时会「画一张图」或下载冒充。  
   → TOOLS 用表格钉死桌面、图库、收件、fixtures 路径；禁止冒充。

4. **发送/接收后用户看不到明确结果**  
   即便工具成功，模型常只回「已处理」，不说完成、不报保存路径。  
   → 增加「聊天窗口回报规则」，与源码里 `【A2A 发送完成】` / `【A2A 文件接收成功】+保存路径` **配套**（双轨：源码给工具结果提示，TOOLS 约束最终对用户话术）。

5. **MIME / 体积踩坑**  
   乱用 `application/octet-stream` 易导致对端落盘成 `.bin`；大文件用错工具会超时或 E2BIG。  
   → 禁止 octet-stream 滥用；文件走 local_file 工具；timeout 提示 ≥ 300000。

**为什么用改 TOOLS.md 这种方式（而不是只改源码）：**

| 做法 | 作用范围 | 局限 |
|------|----------|------|
| 只改插件源码（注册工具、改默认文案） | 工具**存在**且返回结构化提示 | 模型仍可能**不调用**正确工具，或调用后对用户含糊其辞 |
| 改 `TOOLS.md` / `MEMORY.md` | 进入 Agent 工作区上下文，直接影响「该用什么工具、怎么说话」 | 不增加新能力；写错会误导 |
| 两者一起改 | 能力 + 行为约束对齐 | 换机/重装 workspace 时要重新部署 TOOLS |

结论：**源码解决「能不能做」；TOOLS 解决「聊天时会不会做对、会不会说清楚」。** 所以 TOOLS 不是可有可无的文档，而是聊天路径的运行配置。

## 7. 关键设计决策

1. 本机文件 → `a2a_send_local_file`；公网 URI → `a2a_send_file`；SoftBus ≠ A2A。  
2. 手机必须同步 **bundled** 插件目录。  
3. HarmonyOS：`HOME` + `OPENCLAW_STATE_DIR` + 可选钉死 `tasksDir`。  
4. 落盘永远是 `uuid.ext`，不是原文件名。  
5. **源码文案 + TOOLS 规则** 要一起改，聊天体验才稳。  
6. PC DNS 问题用代理属运维，别写进产品默认配置。

## 11. 大文件实测（2026-07-29）

前提：两端 `maxFileSizeBytes`/`maxInlineFileSizeBytes`=52428800；经中继 `ws://121.37.53.35:8001` 内联 base64 隧道；fixture 用 `.mp4` + `video/mp4`（`.bin`/`octet-stream` 不在 MIME 白名单，会即时拒收）。

### 11.1 应用层 50MB 上限（两端）

| 方向 | 文件 | 结果 |
|------|------|------|
| PC→Phone / Phone→PC | `test-51mb.mp4`（≈51.0MB） | **即时拒绝**：`File size 51.0MB exceeds limit 50.0MB`（未走隧道） |

说明：CLI 能显示真实错误，依赖 `respond(false, …, { message })` 热修。

### 11.2 体积阶梯 PC→Phone（`size-ladder`）

| 体积 | 结果 | 耗时 | MD5 |
|------|------|------|-----|
| 5MB | **OK** | ~35s | 源=`d70b177c…` ↔ 收=`d70b177c…` 一致 |
| 10MB | **OK** | ~55s | 源=`fdd21852…` ↔ 收=`fdd21852…` 一致 |
| 15MB | **FAIL** | ~306s | `gateway timeout after 300000ms`；中继侧常伴随对端 disconnect |
| 40MB | **FAIL** | ≥900s 量级 | `gateway timeout` / `Device HW-PC1 disconnected` |

手机收件箱可见：`…3d19c04e….mp4`（5MB）、`…60f10c58….mp4`（10MB）。

### 11.3 Phone→PC 反向

- 小文本与历史中等文件此前可通。
- 本次准备 `rev-10mb.mp4`（MD5 `ed9875e4…`）发起发送时，手机 Wi‑Fi 对中继 `ENETUNREACH` / 后变为 Guest 网 `NotWorking`（疑似 captive portal），**反向 10MB 未完成**。
- 恢复手机外网后应补测：10MB（期望 OK）与 15MB（期望仍超时）。

### 11.4 结论

| 层级 | 实际行为 |
|------|----------|
| 插件配置上限 | **50MB**（超限本地拒收） |
| 中继内联隧道可用上限 | **约 10MB 稳定；15MB+ 超时/断连** |
| 根因倾向 | 整文件 base64 塞进一条/少量 WS 帧，体积放大 ≈4/3，易打满中继/网关超时，而非应用层 50MB 配置本身 |

**产品含义**：对外可继续写「配置支持至 50MB」；运维/TOOLS 应写清 **经当前公网中继的可靠体积约 ≤10MB**；更大文件需分块/直传/对象存储，而不是只调 `maxFileSizeBytes`。
