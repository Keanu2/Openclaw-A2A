# 全链路时延测试报告（聊天窗口形态）

> 测试日期：2026-07-29  
> 环境：HW-PC1（`3QC0225430004479`）↔ HW-Phone1（`FMR0223926019410`）  
> 中继：`ws://121.37.53.35:8001`  
> 插件：`a2a-gateway` / `a2a.send_local_file`（配置上限 50MB）  
> 本文档仅本机查阅，不下发设备  

---

## 1. 测试目的

用接近真实「聊天窗口」的方式，测量：

1. **普通对话时延**（用户发一句话 → Agent 回复）  
2. **不同体积文件**在聊天路径下的全链路时长（用户发指令 → Agent 调工具 → 对端落盘 → 用户可见「发送完成」）  
3. **跨 Agent 要文件**（Agent A 让 Agent B 发文件回来）各环节耗时  

并区分：**LLM 思考/工具选择** vs **A2A 隧道传输** vs **对端 Agent 确认回复**。

---

## 2. 链路定义

### 2.1 普通本机聊天

```text
T0 用户消息进入 Gateway（openclaw agent -m …）
T1 本机 LLM 完成一轮并返回
全链路 ≈ T1 − T0
```

### 2.2 聊天窗口发本地文件（用户 → Agent A → Peer B）

```text
T0 用户在聊天里下发「请把文件发给 HW-Phone1」
T1 本机 Agent 选定并调用 a2a_send_local_file
T2 文件经中继到达 Peer，落盘 /data/local/tmp/a2a-files/<uuid>.ext
T3 Peer Agent 生成「接收成功 + 保存路径」并回传
T4 本机 Agent 对用户说出「发送完成，peer=…，文件名=…」
全链路（用户可感知）≈ T4 − T0
```

### 2.3 跨 Agent 要文件（A 让 B 发文件）

```text
T0 A 侧 a2a.send 文本：「请用 a2a_send_local_file 把 path=… 发给 HW-PC1」
T1 B 侧 Agent 理解并调用 a2a_send_local_file
T2 文件落盘到 A 的 inbox
T3 B 任务完成，A 的 a2a.send 返回
全链路 ≈ T3 − T0（本次实测：文件在返回前已落盘，after_text≈0）
```

### 2.4 直传对照（无本机 LLM）

```text
openclaw gateway call a2a.send_local_file …
→ 含：读盘 + base64 + 中继 + 对端落盘 + 对端 Agent 确认
用于拆出「传输+对端确认」基线，对比聊天路径多出来的本机 LLM 开销。
```

## 4. 结果总表

### 4.1 普通对话时延

| 用例 | 设备 | 全链路 (ms) | 备注 |
|------|------|------------|------|
| 本机闲聊（只回 `pong`，禁止工具） | HW-PC1 | **14,045** | `openclaw agent` 一轮 |
| 本机闲聊（同上） | HW-Phone1 | **16,368** | 同上 |
| 跨端纯文本 A2A | PC→Phone | **20,082** | `a2a.send`；对端自动回了 `HEARTBEAT_OK`（对端 Agent 一轮） |

**结论：** 普通本机聊天约 **14–16 s**；跨端文本还要再加对端 Agent，约 **20 s** 量级。

---

### 4.2 直传阶梯（无本机聊天 LLM，含对端确认）

方向：**PC → Phone**。`elapsed_ms` 为脚本墙钟（含 CLI 启动）；`gateway_ms` 为 gateway 日志中 `a2a.send_local_file` 方法耗时；`peer_task_ms` 为手机侧 `task.finished.duration_ms`（含对端 LLM 回报）。

| 文件 | 大小 | 墙钟 elapsed_ms | gateway_ms | peer_task_ms | 估算纯传输≈ gateway−peer | MD5 |
|------|------|-----------------|------------|--------------|--------------------------|-----|
| chat-tiny.txt | 64 B | 28,143 | 22,200 | 18,763 | ~3.4 s | 一致 |
| chat-1kb.txt | 1 KiB | 22,912 | 16,924 | 12,837 | ~4.1 s | 一致 |
| chat-100kb.mp4 | 100 KiB | 41,026 | 34,985 | 10,425 | ~24.6 s | 一致 |
| Sunflower.jpeg | 81.9 KiB | 43,191 | 37,127 | 22,692 | ~14.4 s | 一致 |
| chat-1mb.mp4 | 1 MiB | 64,190 | 58,076 | 7,934 | ~50.1 s | 一致 |
| chat-5mb.mp4 | 5 MiB | CLI 等待中断* | — | 21,551 | 文件已落盘；PC 中继曾 disconnect | 一致 |

\*5MB：手机 inbox 已有完整文件且 MD5 匹配（`e76aeb13-….mp4`）；发送过程中 PC tunnel 断开，CLI 未收到最终 `RESULT`。按落盘时间相对 1MB 完成点粗估，传输墙钟约 **2–2.5 min** 量级。

**结论：**

- 小文件时延主要被 **对端 Agent 确认（约 8–23 s）** 吃掉，不是磁盘读写。  
- 体积上来后传输变主因：1MB 纯传输约 **50 s**；5MB 约 **2 min+**。  
- 与此前阶梯一致：中继内联可靠区约 **≤10MB**；更大易超时/断连。

### 4.3 聊天窗口发文件（用户 ↔ Agent）

| 用例 | 文件 | 全链路 elapsed_ms | Agent 是否调用 `a2a_send_local_file` | 用户可见话术 | 对端落盘 MD5 |
|------|------|-------------------|--------------------------------------|--------------|--------------|
| 聊天发 tiny | 64 B | **33,652** | 是 | 「发送完成，peer: HW-Phone1，文件名: chat-tiny-via-chat.txt」 | 一致 |
| 聊天发向日葵 | 81.9 KiB | **42,028** | 是 | 「发送完成，peer=HW-Phone1，文件名=Sunflower-via-chat.jpeg」 | 一致 |

相对直传同体积：

| 文件 | 聊天全链路 | 直传墙钟 | 多出的本机 LLM≈ |
|------|------------|----------|-----------------|
| 64 B | 33.7 s | 28.1 s | ~5–6 s |
| 81.9 KiB | 42.0 s | 43.2 s | ~持平（波动） |

**结论：** 在 TOOLS.md 约束下，聊天路径会正确走 `a2a_send_local_file`，并按「发送完成」规则回报；全链路 ≈ **本机 LLM + 直传（含对端确认）**。

---

### 4.4 跨 Agent：A 让 B 发文件

| 用例 | 描述 | text_ms (a2a.send 返回) | 文件出现相对返回 | total_ms | MD5 |
|------|------|-------------------------|------------------|----------|-----|
| Ask-peer tiny | PC 文本指令 → Phone Agent 发回 64 B | **46,691** | after_text_ms=**4**（返回前已落盘） | **46,695** | 一致 |

环节拆解（定性）：

| 环节 | 估计 |
|------|------|
| A→B 文本经中继 | 秒级 |
| B 侧 LLM 理解 + 调 `a2a_send_local_file` | 十余秒级（主导） |
| B→A 文件传输（64 B） | 秒级 |
| B 任务收尾使 A 的 `a2a.send` 返回 | 已含在 46.7 s 内 |

**结论：** 「Agent 让 Agent 发文件」比「用户让本机 Agent 发文件」更慢，因为多一轮 **对端 LLM**；小文件下全链路约 **47 s**。

## 5. 环节耗时对照（汇总）

```text
本机闲聊（无工具）              ≈ 14–16 s
跨端文本（含对端 Agent）        ≈ 20 s
用户聊天发 64B 文件             ≈ 34 s
用户聊天发 ~82KB 图片           ≈ 42 s
直传 1MB（含对端确认）          ≈ 64 s
直传 5MB（文件已到，CLI 曾中断）≈ 2–2.5 min 量级
A 让 B 发 64B 回来              ≈ 47 s
```

经验公式（当前中继 + 当前模型）：

```text
用户可感知发文件时延
  ≈ 本机LLM(选工具/回报) + 隧道传输(随体积↑) + 对端LLM(接收确认)
```

## 6. 正确性与回归点

| 检查项 | 结果 |
|--------|------|
| 聊天是否误用 SoftBus / `a2a_send_file` / 贴 base64 | 本次聊天发文件：**否**，均 `a2a_send_local_file` |
| 是否按 TOOLS 回报「发送完成」 | **是** |
| 对端是否报保存路径 | 直传响应 artifacts 中可见「接收成功」+ 路径 |
| 落盘后缀 | 图为 `.jpg`，文本 `.txt`，视频 `.mp4` |
| MD5 | 本报告所列用例均与源一致 |

## 7. 风险与边界（写入运维预期）

1. **配置 50MB ≠ 中继可靠 50MB**：聊天/直传在公网中继上，实用可靠区约 **≤10MB**；15MB+ 易 timeout/disconnect。  
2. **全链路时延含双边 LLM**：不要把「22 s 发 64B」理解成带宽问题。  
3. **大文件发送中断**：隧道断开后 CLI 可能挂起，但文件有时已落盘——验收应以 inbox + MD5 为准。  
4. **Guest Wi‑Fi / captive portal** 会导致手机 `ENETUNREACH`，表现为对端 not found。

## 9. 一句话结论

在当前 PC↔手机 + 公网中继环境下：**普通聊天约 15 秒；聊天发小文件约 35–45 秒；1MB 约 1 分钟；跨 Agent 要小文件约 47 秒。** 时延由「双边模型 + 内联隧道」共同决定；TOOLS.md 约束使聊天路径稳定走对工具并给出可验收话术。
