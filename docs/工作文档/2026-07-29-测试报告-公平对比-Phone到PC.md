## 1. 公平口径

此前「直传有时比 ask 慢」的报告混用了：

| 问题 | 说明 |
|------|------|
| 方向不同 | 直传常测 PC→Phone，ask 常测 Phone→PC |
| 停表点不同 | 直传含接收端 LLM「接收成功」；ask 的 `a2a.send` 近似发送端任务闭环 |
| wall 虚高 | ask 脚本在 `a2a.send` 返回后仍可能空等 poller，wall 可被虚增 ~120s |

本轮统一为：

1. **同方向**：一律 **Phone → PC**（手机发、PC 收）。
2. **拆隧道 vs LLM**：
   - `file_seen_ms`：PC inbox poller 首次看到匹配 size+MD5 的新文件（近似隧道落盘完成）。
   - 直传 `llm_ack_est_ms = send_elapsed − file_seen`：对端「接收成功」等确认残差。
   - ask `b_after_file_est_ms = a2a_send_text − file_seen`：文件到达后 B 侧收尾残差。
3. **成功标准**：以 **inbox MD5** 为准；大文件时 CLI 可能因本地 gateway WS `1006` / 超大 stdout 报失败，但文件已正确落盘。
4. **主指标**：直传用 `send_elapsed_ms`；ask 用 `a2a_send_text_ms`（及 PC 网关日志中的 `a2a.send Nms`）。**忽略 ask 的 wall_ms**。

```text
直传：Phone a2a.send_local_file → 中继 → PC 落盘 →（可选）接收端 LLM 确认
ask ：PC a2a.send「请发文件」→ Phone LLM 选工具 → Phone a2a.send_local_file → 中继 → PC 落盘
```

备注（20/30MB）：

- 文件已落盘且 MD5 正确；CLI 尾部为  
  `Gateway call failed: Error: gateway closed (1006 abnormal closure)`（目标 `ws://127.0.0.1:18789`）。  
- 这是**本机 gateway 回传超大响应时连接异常关闭**，不是「没传到对端」。成功以 MD5 为准。

解读：

- 隧道时间大致随体积上升：~9s（100KB）→ ~17–18s（1–10MB）→ ~22s（20MB）→ ~33s（30MB）。
- LLM/确认残差也随体积上升（~5s → ~24s），但仍小于隧道本身在大文件时的占比变化。
- **≤30MB 本轮同方向直传全部可验证成功**。

## 4. 同方向对照（核心结论）

| 体积 | 直传 file_seen | 直传闭环 | ask file_seen | ask text 闭环 | 谁更快（闭环） |
|------|----------------|----------|---------------|---------------|----------------|
| 100KB | 9.2s | **14.5s** | 14.8s | 23.0s | **直传** |
| 1MB | 17.2s | **23.2s** | 19.2s | 28.4s | **直传** |
| 10MB | 18.4s | **29.5s** | 26.1s | 42.2s | **直传** |
| 20MB | 22.1s | **39.0s** | 30.5s | 52.4s | **直传** |
| 30MB | 33.3s | **56.9s** | 32.1s | 65.1s | **直传** |
| 40MB | 失败 | 失败 | 失败 | 失败 | 均失败 |

结论：

1. **公平同方向后，直传闭环 consistently 快于 ask**（本轮约少 8–16s），差额主要是 ask 多一轮「理解指令 + 选 `a2a_send_local_file`」。
2. 此前报告里 ask「看起来更快」，来自 **反向流量 + 不同停表**，不是聊天协议本身更快。
3. `file_seen` 上 ask 有时接近甚至略慢于直传：小文件时 ask 的「B 思考」已计入 seen；大文件时两者隧道段同量级。
4. **实用上限**：本环境经公网中继，**30MB 两种模式均可成功**；**40MB 两种模式均失败**（见下节）。

## 5. 40MB + 加长 timeout：能否成功？

### 5.1 配置

两端已从旧默认 ~300s 提到 **1200000ms（20min）**。本轮 40MB 在该预算下实测。

### 5.2 直传 40MB — 失败

| 项 | 值 |
|----|----|
| 结果 | **失败**（inbox 无新文件，MD5 未命中） |
| 客户端耗时 | **1,207,472 ms ≈ 20.1 min** |
| 客户端错误 | `Gateway call failed: Error: gateway timeout after 1200000ms`（`ws://127.0.0.1:18789`） |
| Poller | `POLL_TIMEOUT` waited_ms=1,200,022 |
| Phone 网关 | **没有出现** 40MB 的 `a2a.send_local_file … ✓`；末次成功仍是 30MB（49,351ms） |
| Phone 隧道 | `2026-07-29T02:57:39.506` **`a2a-tunnel: websocket closed`**（开传后约 **1.4 min**） |
| PC 隧道 | 同时段多次 `Device HW-Phone1 disconnected`；接近 20min 末尾还有 `Device HW-Phone1 not found` |

时间线（设备日志 `-05:00`）：

```text
~02:56:16  开始 Phone→PC 直传 L-40mb.mp4
~02:57:39  Phone websocket closed；PC 见 HW-Phone1 disconnected
           （大 payload 传输中继链路已断）
…挂起…
~03:16:31  本地 gateway call 满 1200000ms 超时返回
~03:16:49  Phone 再次 websocket closed；PC 见 disconnected / not found
```

**结论：加长 timeout 不能让 40MB 直传成功。**  
链路在开传后约 1–2 分钟已断开；20 分钟超时只是让客户端多空等，并不恢复中继会话。根因是 **整文件 base64/大帧经公网 WS 中继的稳定性**，不是「5 分钟不够再多给 15 分钟」这种单纯时限问题。

### 5.3 Ask 40MB — 失败

| 项 | 值 |
|----|----|
| 结果 | **失败**（inbox 无新文件） |
| text_ms | 46,861 |
| 错误 | `GatewayClientRequestError: unknown error` |
| PC 日志 | `Device HW-Phone1 disconnected` / 随后 `a2a.send` ~41s `res ✗` |
| Phone | 再次 `websocket closed`（~03:17:23） |

Ask 在直传 40MB 已把隧道打挂之后很快失败；即便隧道短暂重连，**40MB 仍未落盘**。加长 timeout 同样无济于事——错误在约 **47s** 就返回了，并非卡满 20 分钟。

### 5.4 与「应用 50MB 上限」的关系

应用层允许到 50MB ≠ 公网中继路径能稳定送完 40MB。本轮实证：**30MB 成功、40MB 失败**；失败表现为 **中继断开 / 对端丢失 / 本地 call 超时或 unknown error**，而不是「校验拦截超限」。

## 7. 总结

1. **公平同方向（Phone→PC）下，直传闭环快于聊天要文件**；ask 固定多付一轮 LLM 选工具成本。  
2. **100KB–30MB**：直传与 ask **均可成功**（MD5 一致）；大文件直传 CLI 可能假失败，以 inbox 为准。  
3. **40MB**：在 **20 分钟** timeout 下直传与 ask **仍失败**；直传卡满超时，但隧道约 **1.4 min** 已断。  
4. **仅增加 timeout 不能解决 40MB**；需要改传输形态（分片、非整包 base64、更稳的中继/直连），而不是继续加长等待。
