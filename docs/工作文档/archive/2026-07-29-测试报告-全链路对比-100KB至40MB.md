# 全链路对比测试报告：直传 vs 聊天「A 让 B 发文件」（100KB–40MB）

> 测试时间：2026-07-29  
> 设备：HW-PC1 ↔ HW-Phone1，中继 `ws://121.37.53.35:8001`  
> Fixture：两端各自 `a2a-fixtures/L-{100kb,1mb,10mb,20mb,30mb,40mb}.mp4`（内容不同，MD5 分开校验）  
> 原始结果：`D:\openclaw\tmp-device-cfg\ladder-results-v2.jsonl`

---

## 1. 测什么、怎么走

### 1.1 路径 A —— 直接传输（无本机聊天 LLM）

```text
PC: openclaw gateway call a2a.send_local_file
  → 本机读盘 + base64
  → 中继隧道 → Phone 落盘 /data/local/tmp/a2a-files/<uuid>.mp4
  → Phone Agent 生成「接收成功 + 路径」
  → 返回 PC（gateway 方法结束）
```

**计时主指标：** gateway 日志 `a2a.send_local_file … Nms`（含对端确认）；辅以脚本 `elapsed_ms` / inbox MD5。

### 1.2 路径 B —— 聊天形态「A 让 B 把文件传过来」

这是跨 Agent 协作，不是用户本机 `openclaw agent` 闲聊，但等价于聊天里说「让手机把某某文件发给我」时的 **Agent↔Agent 主链路**：

```text
① PC（Agent A 侧）a2a.send 文本：
   「请用 a2a_send_local_file 把 path=… 发给 HW-PC1」
        │
        ▼ 中继
② Phone Gateway 入站 → 派发给 Phone Agent（LLM）
        │
        ▼ TOOLS 约束下调用工具
③ Phone: a2a_send_local_file(path=本机 fixture)
        │
        ▼ 中继（文件 Phone→PC）
④ PC inbox 落盘 /data/local/tmp/a2a-files/<uuid>.mp4
        │
⑤ Phone Agent 回复「发送完成」→ 任务结束
        │
⑥ PC 侧 a2a.send 返回（全链路闭合）
```

**计时主指标：** gateway 日志 `a2a.send … Nms`（从发出「要文件」到 B 整轮任务完成）；inbox MD5 校验。  
说明：本地 poller 曾多等约 120s，**报告以 gateway `a2a.send` 耗时为准**，不以被拉长的 wall 为准。

### 1.3 方向差异（解读对比时必看）

| 模式 | 文件实际飞行方向 |
|------|------------------|
| 直传 | **PC → Phone** |
| A 让 B | **Phone → PC**（A 只发文本指令） |

带宽/中继不对称时，同体积两种模式耗时不必相等；对比的是「用户可感知闭环」与环节构成。

## 2. 聊天窗口整条链路（文字说明）

用户在聊天 UI 里说「让 HW-Phone1 把 L-10mb.mp4 发给我」时，真实经历：

1. **用户 → PC Agent（LLM）**  
   本机一轮推理，决定发 A2A 文本（或直接调工具）。此前单测约 **14–16 s**（无工具闲聊）。
2. **PC Agent → Phone Agent（A2A 文本）**  
   `a2a.send`，peer=`HW-Phone1`。
3. **Phone Agent（LLM）**  
   读 TOOLS：必须 `a2a_send_local_file`，禁止 SoftBus / base64 / `a2a_send_file`。
4. **Phone → PC（文件）**  
   插件读本地绝对路径，经隧道内联传输，PC 落盘 uuid 名。
5. **Phone Agent 回报「发送完成」**；PC Agent 再对用户转述（若走完整聊天）。

本次阶梯为分离变量，**从步骤 2 量到步骤 5**（跳过步骤 1 的本机闲聊 LLM）。若要「用户键入→看见文件」的绝对全链路，需在表中的 ask 耗时上 **再加约 15 s 本机 LLM**（经验值）。

## 4. 环节拆解

### 4.1 直传（以 gateway 为准）

```text
全链路 ≈ T_encode_tunnel_save + T_peer_LLM_ack

其中：
  T_peer_LLM_ack  — Phone 收到文件后 Agent 说「接收成功」（小文件时常占大半）
  T_encode_tunnel_save — 随体积明显上升（10MB→30MB 可见）
```

经验观察：

- **≤1MB**：对端确认 LLM 与传输量级接近，总时长约 **17–30 s**。  
- **10–30MB**：传输变主因，约 **41–91 s**。  
- **40MB**：本轮中继路径失败（超时/未落盘）。

### 4.2 Ask 聊天（A 让 B）

```text
全链路(从 a2a.send 起) ≈
  T_text_relay          （秒级）
+ T_B_LLM_理解选工具     （十余秒级，几乎总有）
+ T_file_relay_B→A      （随体积↑）
+ T_B_收尾回复           （含在 task.finished 内）
```

对照：

| 体积 | ask 全链路 | 同体积直传 | 差额（ask − direct） |
|------|------------|------------|---------------------|
| 100KB | 17.4 s | 17.4 s | ~0 |
| 1MB | 18.4 s | 29.9 s | ask 更快* |
| 10MB | 33.4 s | 52.5 s | ask 更快* |
| 20MB | 45.7 s | 41.1 s | 接近 |
| 30MB | 56.6 s | 90.7 s | ask 更快* |
| 40MB | 失败 | 失败 | 均失败 |

\*方向相反（Phone→PC vs PC→Phone），且直传含「接收方 LLM 确认」、ask 的 `a2a.send` 以发送方任务完成为准，**不宜解读成 ask 一定更省带宽**；只说明两种闭环都在 30MB 内可完成。

### 4.3 若从「用户打字」算起（估算）

| 场景 | 估算公式 |
|------|----------|
| 用户让本机直接发文件 | ≈ 本机 LLM(选工具) **+15 s** + 直传表 |
| 用户让 A 去叫 B 发文件 | ≈ 本机 LLM **+15 s** + ask 表（`a2a.send`） |

例：用户聊天「让手机把 10MB 发过来」≈ **15 + 33 ≈ 48 s**（量级）。

---

## 5. 对比结论

1. **100KB / 1MB / 10MB / 20MB / 30MB**：直传与「A 让 B」**均可成功**，MD5 一致。  
2. **40MB**：两种路径本轮均失败（直传空等约 15 min；ask 约 42 s 返回失败且无落盘）。  
3. **Ask 路径多一轮 B 侧 LLM**，但小文件时总时长仍常落在 **20–60 s**，因为文件发送被包进同一任务。  
4. **实用上限**：本轮环境可到 **30MB**；**40MB 仍不可靠**（与早期「15MB 易挂」相比，网络更好时上限上移，但 40MB 未过）。  
5. **聊天要稳**：依赖 TOOLS 强制 `a2a_send_local_file`；否则 B 会走错工具导致 ask 失败。

---

## 6. 失败与噪声说明

| 现象 | 说明 |
|------|------|
| 直传 20/30MB CLI `ok=false` 但 inbox MD5 对 | hdc 回传超大 JSON 被截断；以 gateway ✓ + MD5 为准 |
| Ask 脚本 EXIT=1 但 MD5 对 | 本地 FILE_SEEN poller 未点名到文件后又空等 ≤120 s；以 gateway `a2a.send` + inbox-diff 为准 |
| 早期 15MB 失败 vs 本轮 30MB 成功 | 中继/Wi‑Fi 波动大；上限是「环境+体积」联合结果 |

---

## 7. 一句话

在 100KB→30MB 阶梯上，**直接 `a2a.send_local_file` 与聊天式「A 让 B 发文件」都能跑通且 MD5 正确**；全链路大约 **17 s（100KB）到约 1–1.5 min（30MB）**。聊天 ask 路径 = 文本指令 + 对端 Agent 选工具 + 反向传文件，gateway 上就是一次 `a2a.send` 的时长。**40MB 两种方式均失败**，产品预期仍应把可靠区写在 **≤30MB（本轮）/ 更保守 ≤10MB（弱网）**，而不是配置里的 50MB。
