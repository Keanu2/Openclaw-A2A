# 公平对比测试报告：直传 vs 聊天「A 让 B 发文件」

> 测试时间：2026-07-29  
> 设备：HW-PC1 (`3QC0225430004479`) ↔ HW-Phone1 (`FMR0223926019410`)  
> 中继：`ws://121.37.53.35:8001`  
> Fixture：两端 `a2a-fixtures/L-{100kb,1mb,10mb,20mb,30mb,40mb}.mp4`（内容/MD5 各自独立）  
> 超时实验：两端 `tunnel.requestTimeoutMs` / `agentResponseTimeoutMs` / `agents.defaults.timeoutSeconds` 提到 **1200000 ms（20 min）**  
> 原始片段：终端 `432756` / `58383` / `58384`；结果追加 `D:\openclaw\tmp-device-cfg\fair-results.jsonl`

---

## 1. 公平口径（相对上一份阶梯报告）

上一份 `2026-07-29-测试报告-全链路对比-100KB至40MB.md` 里：

| 模式 | 文件方向 | 停表点 |
|------|----------|--------|
| 直传 | PC → Phone | `a2a.send_local_file` 返回（含接收方 LLM「接收成功」） |
| A 让 B | Phone → PC | `a2a.send` 返回（含发送方 LLM 选工具+发完） |

因此「直传有时更慢」**不等于**直传协议更慢，而是方向 + 计时口径不同。

本报告公平化：

1. **同方向**：主表统一为 **Phone → PC**（直传与 ask 都是手机发、PC 收）。  
2. **拆隧道 vs LLM**：用 inbox poller 的 `FILE_SEEN.from_poll_ms` 近似「文件到达」时间；其余为 LLM/确认残差。  
3. **不以被拉长的 wall 为准**：ask 脚本在 `a2a.send` 返回后仍可能空等 poller，wall 可被虚增到 ~140–160 s。

```text
file_seen_ms     ≈ 编码 + 中继 + 对端落盘（隧道主路径）
llm / 残差       ≈ send_elapsed − file_seen（直传：对端「接收成功」）
                   或 a2a_send − file_seen（ask：B 侧理解/选工具/收尾）
```

## 2. 同方向结果：Phone → PC

### 2.1 直传（手机 `a2a.send_local_file` → PC inbox）

| 体积 | 结果 | file_seen_ms | send_elapsed_ms | llm_ack_est | MD5 | 备注 |
|------|------|--------------|-----------------|-------------|-----|------|
| 100KB | **成功** | **10,806** | **13,946** | **3,140** | 一致 | CLI ok |
| 1MB | **成功** | **11,608** | **19,624** | **8,016** | 一致 | CLI ok |
| 10MB | **成功** | **~31–36.5k** | **36,549**（复核） | 小（复核轮） | 一致 | 首轮 CLI 误判 `E2BIG`（base64 子串）；复核 statusCode 200 |
| 20MB | **成功** | （poller 未点名） | CLI 常 **Signal 9** | — | **一致** | 传完后手机编码进程被杀；以 inbox MD5 为准 |
| 30MB | **成功** | （同上） | CLI 常失败/被杀 | — | **一致** | 同上 |
| 40MB | （本轮主测为 PC→Phone，见 §4） | — | — | — | — | Phone 侧大文件 encode 极易 OOM |

解读：

- **≤1MB**：隧道约 **11 s**，LLM 确认约 **3–8 s**，总闭环约 **14–20 s**。  
- **10MB**：隧道约 **30–37 s**，闭环约 **37 s**。  
- **20/30MB**：文件能落到 PC 且 MD5 对，但手机 CLI/进程常在超大 stdout/base64 后被杀——**传输成功 ≠ CLI 干净退出**。

### 2.2 聊天 A 让 B（PC `a2a.send` 文本要文件 → 手机发回）

文件方向同样是 **Phone → PC**。

| 体积 | 结果 | file_seen_ms | a2a_send_ms | B 残差估 (send−seen) | MD5 | wall（勿作主指标） |
|------|------|--------------|-------------|----------------------|-----|-------------------|
| 100KB | **成功** | **16,409** | **22,503** | **~6.1 s** | 一致 | ~143 s |
| 1MB | **成功** | **18,012** | **26,074** | **~8.1 s** | 一致 | ~150 s |
| 10MB | **成功** | **25,657** | **41,854** | **~16.2 s** | 一致 | ~161 s |
| 20/30MB | 本轮公平 ask 未完整重跑 | — | — | — | — | 旧阶梯 ask 同方向曾成功（见旧报告） |
| 40MB | 旧阶梯失败 | — | ~42 s `res ✗` | — | 未收到 | — |

Ask 拆解：

```text
a2a.send ≈ T_text_relay + T_B_LLM_选工具 + T_file_relay + T_B_收尾
file_seen ≈ 到「PC 看见文件」为止（含 B 理解+传文件，不含/少含收尾）
```

小文件时 `file_seen` 已含 B 的「理解+调工具」；残差主要是发完后的 Agent 收尾回复。

## 3. 同方向对照（Phone→PC）

| 体积 | 直传 file_seen | 直传闭环 | ask file_seen | ask `a2a.send` | 谁更快（闭环） |
|------|----------------|----------|---------------|----------------|----------------|
| 100KB | 10.8 s | **13.9 s** | 16.4 s | 22.5 s | **直传**（少一轮「请发文件」LLM） |
| 1MB | 11.6 s | **19.6 s** | 18.0 s | 26.1 s | **直传** |
| 10MB | ~31–37 s | **~37 s** | 25.7 s | 41.9 s | **直传闭环略快**；ask 的 file_seen 更短（含不同调度抖动） |

结论（公平同方向后）：

1. **直传通常不比 ask 慢**——上一份报告里 ask「更短」主要来自反向带宽 + 不同停表点。  
2. Ask 固定多一段「B 理解指令并选工具」；小文件时这段与隧道同量级（数秒～十几秒）。  
3. 应用产品预期：≤10MB 两种路径都稳；20–30MB 直传可落盘但手机侧易 OOM/杀进程；40MB 仍不可靠。

## 4. 40MB + 加长 timeout：能否成功？

### 4.1 配置变更

两端已从默认 **300000 ms（5 min）** 提到：

- `plugins.entries.a2a-gateway.config.tunnel.requestTimeoutMs = 1200000`  
- `…timeouts.agentResponseTimeoutMs = 1200000`  
- `agents.defaults.timeoutSeconds = 1200`  

CLI `--timeout` / 脚本 timeout 同步到 ≥1200 s。备份：`openclaw.json.bak.fair`。

### 4.2 本轮实测（直传 PC → Phone，`L-40mb.mp4`）

| 项 | 值 |
|----|-----|
| 源 MD5 | `0407f38414fe790a1a7abe71ab9435e0`（40 MB） |
| 结果 | **失败** |
| 耗时 | **elapsed_ms ≈ 1,209,389**（约 **20.2 min**） |
| 错误原文 | `Gateway call failed: Error: gateway timeout after 1200000ms` |
| Gateway target | `ws://127.0.0.1:18789`（本机 loopback RPC） |
| Phone inbox | **无** 新 40MB 文件；poller 输出 `poll-40.txt` 最终亦不可见 / 无 `FILE_SEEN` |
| 进程观察 | 约 15:14–15:33 一直停在 `DIRECT_START`，满 1200s 后 `DIRECT_DONE ok=false` |

### 4.3 失败原因（详细）

**不是**应用层 50MB 拒收（那种会立刻 `File size … exceeds limit 50.0MB`）。

分层：

1. **外层可见错误**  
   OpenClaw CLI 等本机 gateway RPC **整整 1200000 ms** 无结果 → `gateway timeout after 1200000ms`。  
   说明：把超时从 5 分钟加到 20 分钟，**只是把失败推迟到 20 分钟**，并没有让传输完成。

2. **为何 RPC 一直不返回**（综合本轮与更早 40MB 日志）  
   - 40MB 二进制经 **整文件 base64** 后约 **~53MB+** 文本，要经 WebSocket 中继一次推完。  
   - 早期失败常见：`Tunnel timeout: 300000ms`、对端 `disconnected`、`All transports failed`。  
   - 本轮在 timeout 提到 20 min 后，CLI 仍在满额超时；手机 inbox **始终没有**对应体积/MD5 文件 → 隧道侧**从未完成落盘**（卡住、中继丢大帧、或对端在解码/写盘前断连）。  
   - 网关在重启后的短日志窗口里看不到清晰的 `send_local_file ✓`；与「方法未正常结束」一致。

3. **设备侧次要因素**  
   - 手机大体积 encode / 超大 stdout 易 **Signal 9 / OOM**（20–30MB 已出现：文件到了但 CLI 被杀）。  
   - 40MB 更重，即使超时再长，内存与中继一次性帧大小仍可能先挂。

### 4.4 对「加 timeout 能否救 40MB」的结论

| 问题 | 答案 |
|------|------|
| 只加长 timeout，40MB 能成功吗？ | **本轮不能。** 20 min 后仍 `gateway timeout`，inbox 无文件。 |
| 根因是 timeout 太短吗？ | **部分曾经是**（旧 5 min 隧道超时）；**加长后仍失败** → 还有 **中继/整包 base64 体积、稳定性、设备内存** 等硬限制。 |
| 配置 50MB 上限有意义吗？ | 本地拒收 >50MB 仍有效；**可靠传输上限远低于配置上限**，本环境约 **≤30MB（落盘）/ 更稳 ≤10MB**。 |

要真正做大文件，需要改传输形态（分片、非 base64 整包、直连/旁路通道等），而不是继续堆 timeout。

## 5. 噪声与判定规则（公平测试踩过的坑）

| 现象 | 正确判定 |
|------|----------|
| CLI `fail_hint=e2Big` / stdout 含 `E2BIG` | 可能是 **base64 正文子串**误匹配；看 `statusCode: 200` + inbox MD5 |
| CLI Signal 9 / exit≠0，但 PC 有新文件且 MD5 对 | **传输成功**，进程在回传超大 JSON 时被杀 |
| ask `wall_ms` ~140–160 s | 本地 poller 空等；用 **`a2a_send_ms` + `file_seen_ms`** |
| `hdc shell` 超长 argv | 「parameter -t too long」；改用设备上短脚本 |

---

## 6. 总结论

1. **同方向（Phone→PC）公平对比**：直传闭环在 100KB/1MB/10MB 上 **短于或接近** ask；ask 多付「B 理解+选工具」成本。  
2. **隧道 vs LLM**：小文件 LLM 残差数秒；随体积增大，`file_seen` 主导增长。  
3. **20–30MB**：同方向直传可 MD5 成功，但手机 CLI 不稳定。  
4. **40MB + 20 min timeout**：**仍失败**；错误为 `gateway timeout after 1200000ms`，对端无落盘。加 timeout **不能**单独解决问题。  
5. 产品表述建议：配置可写 50MB，**对外可靠区写 ≤10–30MB（视网）**；40MB 需换传输实现后再测。

---

## 7. 一句话

公平同方向后，直传并不系统性慢于「聊天要文件」；40MB 把 timeout 提到 20 分钟仍在满额 gateway 超时且无 inbox 落盘——失败已超出「超时太短」，属于整包 base64 中继路径的硬瓶颈。
